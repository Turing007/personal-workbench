## 0. 摘要（一页结论）

| 问题 | 结论 |
| --- | --- |
| 技术上能不能做？ | **能**。服务端（Fastify + SQLite）可原样复用；共享业务逻辑（约 2500 行）可直接复用；需重写的是手机端界面层。 |
| 真正的门槛在哪？ | 不在技术，在平台侧三道关：**① 小程序账号主体**（个人主体的能力受限）**② 小程序备案**（新规，管局审核 1~20 个工作日）**③ 审核**（有登录墙的工具类需提供测试账号，纯网页套壳容易被拒）。 |
| 给谁用，值不值？ | **给自己/家人手机管订单**：现有安卓壳 + PWA 已覆盖约九成，小程序新增收益有限（免装 APK、微信直达），且打印、大视频上传、导出落盘仍有硬性缩水 → **维持现状即可，不建议整站搬**。<br>**给客户看图册**：收益明确 —— 微信里发一张小程序卡片，客户点开即看、加载快、可收藏转发，胜过现在"发网页链接" → **明显值得做**。 |
| 我的建议 | **从「客户图册」小程序起步**（路线 C，3~5 个开发日出第一版，备案并行办理），跑顺后如果还想在手机上管订单，再把管理端模块逐个加进同一个小程序，而不是另做一个。 |
| 一个前置硬条件 | 服务器域名这道关**已经过了**：vigortech.xyz 已完成 ICP 备案（鄂ICP备2026056865号）+ HTTPS 已在用，这是很多小程序项目卡最久的一步。剩下的主体资质问题需要你拍板（见第 8 节）。 |

## 2. 微信平台规则逐条核对

| # | 平台规则 | 对本项目的影响 | 结论 | 适配成本 |
| --- | --- | --- | --- | --- |
| 1 | 只能请求后台配置过的「合法域名」，必须 HTTPS，域名须 ICP 备案 | vigortech.xyz 已备案、已有 HTTPS | ✅ 已满足 | 后台填 4 类域名（request/uploadFile/downloadFile + 业务域名），往服务器放一个校验文件（Caddy 加一段静态路由） |
| 2 | 小程序自身也要 ICP 备案（2023-09 起新小程序须备案才可上架），各省管局 1~20 个工作日 | 未办理 | ⚠️ 必须办 | 纯等待，可与开发并行；个人主体也可备案 |
| 3 | **个人主体**：不能使用 web-view；开放类目有限。**企业/个体工商户**：能力全、类目广 | 未知你的主体类型 | ⚠️ 需拍板 | 若只有个人身份且路线涉及 web-view 或类目不匹配 → 办个体工商户（线上可办，几天到一两周） |
| 4 | 小程序没有浏览器式 Cookie 会话；常规做法是登录后发 token 放请求头 | 服务端现在用 Cookie 会话 | ⚠️ 小改造 | 服务端加一条"token 登录"通道（复用现有会话表），1~2 个开发日 |
| 5 | 有账号体系的小程序审核时必须提供可体验全部功能的测试账号；"不登录什么都用不了"是常见驳回原因 | 现在的界面全在登录墙后 | ⚠️ 审核风险 | 让小程序首页包含免登录内容（图册页天然满足） |
| 6 | `<image>` 组件不能带自定义鉴权头，不能依赖 Cookie 拉图 | 图片/缩略图现在都过会话鉴权 | ⚠️ 小改造 | 给图片出口加 token 查询参数（沿用图册 token 机制，服务端已有雏形） |
| 7 | 上传走 `wx.chooseMedia` / `wx.uploadFile`（可多选、可压缩）；**没有** Ctrl+V 粘贴图片 | 桌面端高频用粘贴传凭证 | ✅ 影响小 | 手机端本来就是相册选图；粘贴留桌面端 |
| 8 | 小程序没有安卓壳那样的"前台保活"，切后台/锁屏可能中断上传；200MB 视频长传风险大 | 安卓壳专门做了上传保活 | ❌ 不建议做 | 大视频上传保留电脑/壳；小程序不做或降到小图小文件 |
| 9 | 导出文件可用 `downloadFile` + `openDocument` 预览（支持 pdf/xlsx/docx 等），但文件在沙箱里，可"转发给微信好友/文件传输助手" | 壳内落盘 + 系统分享 | ✅ 可替代 | 一期不做的话留二期 |
| 10 | 小程序没有打印 API | 打印本来就只在电脑端 | ✅ 无影响 | 箱唛打印继续电脑端 |
| 11 | 没有 Service Worker；可用本地 storage 做缓存 | PWA 的离线只读 | ⚠️ 弱化 | 离线只读可简化重做或放弃，非关键功能 |
| 12 | 包体积：主包/单个分包 ≤2MB，总分包 ≤30MB | 现有前端产物 750KB JS + 888KB CSS/资源 | ✅ 可行 | 需分包策略；React 类框架运行时注意主包瘦身 |
| 13 | 支持深色模式（app.json 声明 + 主题文件） | 现有深浅色跟随系统 | ✅ 可保留 | 小 |
| 14 | 微信支付：本项目不涉及在线收款 | 无 | ✅ 无需申请 | 0（顺带规避 iOS 虚拟支付一类合规问题） |

## 3. 四条路线对比

| | 路线 A：web-view 套壳 | 路线 B：重写管理端 | 路线 C：客户图册小程序（推荐起步） | 路线 D：维持现状 |
| --- | --- | --- | --- | --- |
| 做法 | 一个小程序，一个页面，直接装现有网页 | 用 React 语法的跨端框架（Taro）把手机端高频模块重写成原生小程序页面 | 独立小程序，只做"公司介绍 + 产品图册"，数据来自现有图册服务 | 安卓壳 + PWA + 图册链接 |
| 前置条件 | **企业/个体工商户主体**（个人主体禁用 web-view） | 主体 + 备案 | 主体 + 备案 | 无 |
| 开发量 | 1~2 个开发日 | 一期 12~18 个开发日；全量 40+ | 3~5 个开发日 | 0 |
| 主要问题 | 审核对"纯网页套壳"不友好；web-view 里导出/选图体验同浏览器；登录墙照旧 | 三端（电脑网页/安卓壳/小程序）并行维护；审核要测试账号 | 功能单一，但正好是真实且高频的场景 | iOS 用户只能走 PWA；分享体验一般 |
| 适合 | 想用 5 分钟验证通道 | 确定长期在微信里办公 | **先给客户用起来** | 自己够用就收 |

补充说明：

- **路线 A 不推荐**：套壳本质是"把网页装进小程序"，既没吃到原生能力，还可能因为"功能全在网页里"被审核质疑；对个人主体还是死路。
- **路线 B 的真实成本**不只在开发：以后每加一个功能，电脑网页、小程序两边都要做一遍。**建议只把手机上真正高频的模块搬过去**（见第 5 节），不做全量对齐。
- **路线 C 的好处**：图册是免登录的展示内容，审核最顺（不踩"登录墙"驳回点）；它跟现有 `/c/:token` 图册共用同一份数据，客户拿到的还是同一批图和价格说明；后续要加管理端，直接在这个小程序里加"登录入口"即可平滑演进成路线 B。
- 朋友圈限制：小程序分享到微信聊天天然支持；直接分享朋友圈有限制（仅特定场景/类目），对图册场景影响不大，客户仍可通过聊天转发。
- 备案和审核是**日历等待**（各 1~20 个工作日 / 每轮 1~7 天），不是开发工作量，可与开发并行。

## 4. 推荐路线与分期

**推荐：路线 C 起步，按需演进。**

- **一期（图册小程序）**：公司信息（名称、logo、微信二维码、电话地址）+ 产品图册（分类浏览、大图查看、参数）。数据复用现有图册服务和产品图，新增 1 个免登录只读 JSON 接口。
- **二期（视一期效果）**：在同一小程序里加登录 + 手机高频管理模块（订单查看/状态流转、报价、发货、财务只读）。
- **明确不进小程序**：箱唛打印（电脑端）、备份恢复、200MB 视频上传、桌面级批量操作。

理由汇总：一期投入小（几天）、审核风险低、直接服务"把图册发出去"这个已经存在的真实场景；就算二期不做了，一期也不浪费。

## 5. 功能取舍清单（若走二期）

| 模块 | 建议 | 理由 |
| --- | --- | --- |
| 订单列表 / 详情 / 状态流转 | 做（二期一期批） | 手机最高频 |
| 新建订单 | 做 | 表单折单列，手机填单是真实场景 |
| 报价 / 销售单查看 | 做 | 与订单同构，复用页面 |
| 发货管理 | 做 | 手机顺手确认发货 |
| 财务 | 只读 | 录入低频，保留电脑端 |
| 产品库浏览 | 做（轻编辑可选） | 现场给客户展示也用得上 |
| 在线图册 | 一期就做 | 本报告推荐主线 |
| 箱唛编辑 / 打印 | 不做 | 依赖电脑和打印机 |
| 备份 / 恢复 | 不做 | 大文件与沙箱限制 |
| 视频上传 / 大附件 | 不做或降级 | 小程序无保活，长传不可靠 |
| 售价计算器 | 暂不做 | 桌面外使用频率待观察，二期再看 |
| 账号与安全（改密码等） | 二期尾 | 低频 |

## 6. 工作量与时间线

开发工作量（按"你 + AI 助手"的现有节奏估，单位为开发日）：

| 项 | 工作量 |
| --- | --- |
| 服务端适配（token 登录通道、图片 token 出口、图册 JSON 接口、Caddy 校验文件路由） | 2~3 个开发日 |
| 小程序端 · 图册一期（3~4 个页面 + 真机调试） | 2~4 个开发日 |
| 小程序端 · 管理模块二期（订单/报价/发货/财务只读等） | 10~15 个开发日 |
| （不建议）全量对齐 | 40+ 个开发日 |

日历时间（可与开发并行）：

- 注册小程序账号：当天可好（企业/个体户需营业执照；个人只需身份证）
- **小程序备案：管局 1~20 个工作日**（个人主体也可办）
- 首轮审核：1~7 天，可能多轮（准备测试账号可显著减少驳回）

时间线（理想情况）：第 1 天注册并提交备案 → 备案等待期内完成一期开发和真机预览（开发版/体验版不需要审核，可先给家人和客户预览）→ 备案通过后提交审核上架。

## 7. 风险清单

| 风险 | 概率 | 影响 | 缓解 |
| --- | --- | --- | --- |
| 审核驳回（登录墙 / 套壳 / 类目不匹配） | 中 | 上线延后 | 首页放免登录图册页；管理功能登录后进入；提审带测试账号；注册时先核对类目 |
| 主体只有个人身份，web-view 不可用、类目受限 | 未知 | 决定路线 A 死、B/C 类目收窄 | 办个体工商户；或在注册时用官方类目表核对"产品展示/公司介绍"所需类目 |
| 备案被卡（资料不一致） | 低 | 上线延后 | 尽早提交，主体信息与域名备案信息保持一致 |
| 三端并行维护漂移 | 中 | 长期成本 | 小程序只做高频子集；接口共用一套（不复制服务端逻辑） |
| 小程序端体验回退（大文件、打印） | 确定 | 可接受 | 明确保留电脑/安卓壳承担这些场景 |
| 存储/登录态差异引入安全面（token 泄露、分享链接扩散） | 低 | 数据安全 | token 走 header + 有效期；图片出口 token 只读图册范围；沿用现有登录限流 |

## 8. 待拍板的问题与下一步

需要你确认两件事，路线随之确定：

1. **主体资质**：你有营业执照/个体工商户吗，还是只有个人身份？（决定路线 A 是否可行、类目选择空间）
2. **主要给谁用**：客户看图册 / 自己家人手机办公 / 两者都要？（决定做路线 C 还是 C→B）

我的建议（若两者都要）：**先做路线 C（图册）**，同时把服务端那几个小接口适配一次做掉（token 登录、图片出口），为二期的管理端铺好路。

确认后我可以按项目惯例出一份《小程序改造需求》md（范围、接口、页面、验收口径），再开工。
