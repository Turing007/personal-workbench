# 订单日期、客户产品与包装信息兼容升级规格

**状态：** 待用户审查

**目标：** 在不破坏现有产品、订单和箱唛历史数据的前提下，简化客户产品录入，支持订单内直接添加新品，并将系统产品库包装方式改为内盒/外箱的单字段尺寸结构。

## 1. 范围与设计原则

本次升级包含四个相互关联的部分：

1. 新建订单的下单时间改为日期精度；
2. 客户产品库改为面向订单的最小字段模型；
3. 订单选择产品无匹配时，可以在当前订单流程中快速添加新品；
4. 系统产品库包装方式增加内盒信息，并将内盒、外箱尺寸改为单个文本输入框。

采用兼容升级方式：

- 不删除现有数据库列，不清理 `data/`，不批量改写已有订单或已有产品；
- 新界面只展示本次确认的字段；
- 新接口优先使用新字段，同时继续接受旧字段，保证已有前端调用和历史数据可读取；
- 订单箱数以客户产品的装箱数为唯一计算依据，计算公式为 `ceil(数量 ÷ 装箱数)`；
- 相同品名但规格不同，视为不同客户产品，选择和保存时必须保留规格差异。

本次不改变订单状态流转、手动合箱、箱唛编辑/打印、备货和发货的既有业务规则；只为这些功能提供正确的日期、产品装箱数和包装数据。

## 2. 新建订单下单时间

### 2.1 界面行为

- 新建订单使用 `input type="date"`，显示格式为 `YYYY-MM-DD`，例如 `2026-08-11`。
- 编辑历史订单时仍显示原订单的日期部分；如果历史值是 ISO 日期时间，只截取前 10 位显示，不改写数据库中的历史原值。
- 新订单默认使用浏览器本地日期，不通过 `new Date('YYYY-MM-DD')` 或 UTC ISO 转换生成，避免中国时区下出现前一天。
- 日期为必填项；用户不能输入时间、时分或秒。

### 2.2 数据和接口行为

- 新建订单保存时，前端直接发送日期字符串，不做 `Date -> ISO` 转换。
- 后端接受 `YYYY-MM-DD` 并按原字符串保存。
- 为兼容编辑旧订单，后端仍接受已有 ISO 日期时间值，保存时保留其日期部分；不对历史订单做批量迁移。
- 后端校验日期必须是有效的公历日期，格式不是 `YYYY-MM-DD` 且不能被兼容解析的值返回参数错误。
- 订单列表、订单详情、箱唛和打印历史继续使用既有接口结构；展示层统一将日期时间数据格式化为日期，不因本次升级丢失历史记录。

## 3. 客户产品库

### 3.1 用户可维护字段

客户产品的添加和编辑界面只显示、只要求以下四个字段：

| 字段 | 规则 |
| --- | --- |
| 品名 | 必填，保存前去除首尾空格 |
| SKU | 可为空，保存前去除首尾空格 |
| 规格 | 可为空，保存前去除首尾空格 |
| 装箱数 | 必填正整数，最小值为 1 |

客户产品界面不显示系统产品字段：分类、采购价、供应商、参数、包装方式、图片、颜色、插脚、配件和备注。客户产品列表至少显示品名、SKU、规格、装箱数和操作按钮。

### 3.2 数据兼容

- `customer_products` 既有表结构保留，包含旧的 `packaging_json`、`remark` 等字段，已有客户产品不删除。
- 新建客户产品使用一个默认包装记录保存装箱数，包装名称可为空；客户产品的装箱数读取该默认记录的 `packCount`。
- 读取旧客户产品时，优先读取其第一个有效包装记录的装箱数；若旧记录没有有效装箱数，则显示 `1`，并在用户保存时要求明确确认/修改为正整数。
- 编辑客户产品只更新品名、SKU、规格和默认包装装箱数，不清空数据库中未在新界面暴露的旧备注、供应商或其他兼容字段。
- 旧的多包装数组可以继续被后端读取；本次简化界面不展示、不新增多种客户产品包装方案，也不删除旧数组中的其他记录。
- 相同品名不同规格不做合并。客户产品的搜索结果同时显示品名、SKU、规格和装箱数，用户通过规格区分产品。

### 3.3 订单中的装箱数和箱数

- 从客户产品库选择产品后，订单明细自动带出品名、SKU、规格和装箱数。
- 订单明细允许用户调整本单装箱数；这个值是订单快照，不会反向修改客户产品库。
- 订单箱数始终由订单明细的数量和装箱数自动计算：

  `箱数 = ceil(订购数量 / 本单装箱数)`

- 数量或本单装箱数发生变化时立即重新计算；数量和装箱数均限制为正整数。
- 箱数不是用户直接编辑的字段。订单总箱数为各产品行箱数之和，并继续供箱唛、发货表和后续手动合箱流程调用。

## 4. 新建订单直接添加新品

### 4.1 触发方式

订单产品选择区域保留“添加新品”入口，并在按品名、SKU、规格搜索无匹配时显示“添加新品”按钮，而不是只显示提示文字。

两种入口复用同一个简化编辑流程：

- 点击搜索结果中的按钮，打开当前订单流程内的新品弹窗；
- 点击订单产品区顶部按钮，打开同一个新品弹窗。

搜索词可作为新品弹窗中“品名”的初始值，用户可以修改或清空；搜索词不会被强制写入 SKU。

### 4.2 新品弹窗

弹窗只包含：品名、SKU、规格、装箱数，以及“保存并加入订单”“取消”按钮。

保存规则：

1. 校验品名非空、装箱数为正整数；
2. 调用客户产品接口保存四个字段；
3. 保存成功后刷新客户产品列表；
4. 将接口返回的客户产品自动加入当前订单明细；
5. 自动带出本单装箱数，并按当前数量计算箱数；
6. 关闭新品弹窗，保留订单表单中已填写的其他内容。

保存失败时保留弹窗内容并显示错误，不将不完整产品加入订单。关闭订单表单或取消新品弹窗时，不保存草稿中的半成品。

## 5. 系统产品库包装方式

### 5.1 新界面字段

系统产品的包装方式仍然是一种包装一行，表格列调整为：

| 分组 | 字段 | 规则 |
| --- | --- | --- |
| 基础 | 包装名称 | 例如“彩盒包装”“塑像包装”，可自定义 |
| 内盒 | 尺寸 | 一个文本输入框，例如 `35×28×20cm` 或 `40*30*25` |
| 内盒 | 重量 | 非负数字，单位沿用现有界面约定 |
| 外箱 | 尺寸 | 一个文本输入框，例如 `40×30×25cm` 或 `40*30*25` |
| 外箱 | 重量 | 非负数字，单位沿用现有界面约定 |
| 外箱 | 装箱数 | 正整数 |

尺寸不拆成长、宽、高三个控件。系统产品可添加多行包装方式，每行独立维护上述内盒和外箱信息；删除行前沿用现有确认/交互规则。

### 5.2 数据库兼容迁移

在 `product_packaging` 表新增以下列，不删除旧列：

```sql
inner_size TEXT NOT NULL DEFAULT ''
inner_weight REAL NOT NULL DEFAULT 0
outer_size TEXT NOT NULL DEFAULT ''
```

旧列 `outer_length`、`outer_width`、`outer_height`、`outer_weight`、`pack_count` 保留，继续服务历史订单和旧接口。

迁移必须在现有迁移事务中通过 `PRAGMA table_info(product_packaging)` 检查列是否存在，不存在时逐列 `ALTER TABLE ... ADD COLUMN`。初次创建数据库时，`CREATE TABLE` 直接包含新列。迁移版本递增到当前版本 `5`，已有数据不重建、不删除、不覆盖。

### 5.3 读写规则

- 新接口字段为 `name`、`innerSize`、`innerWeight`、`outerSize`、`outerWeight`、`packCount`；后端同时接受旧的 `outerLength`、`outerWidth`、`outerHeight` 字段。
- 读取新记录时，界面使用 `inner_size` 和 `outer_size`；读取旧记录时，将非零旧长、宽、高拼接为一个尺寸文本，例如 `35×28×20`，填入对应的外箱尺寸。
- 新保存时同时写入新字段和旧字段：
  - 新尺寸文本保存到 `inner_size`/`outer_size`；
  - 若尺寸文本包含三个可识别数字，则同步填充对应旧长、宽、高，供旧逻辑使用；
  - 无法解析为三个数字时，旧长、宽、高保持为 `0`，不篡改用户输入的新尺寸文本；
  - 重量和装箱数同步写入新旧共用/兼容字段。
- 旧接口只发送旧字段时，后端正常保存并在读取时提供组合后的新尺寸文本。
- 包装名称、内盒信息、外箱信息和装箱数在产品详情、编辑回显及报价单/订单调用产品信息时保持一致；本次不改变报价单的产品快照机制。

## 6. 前后端模块边界

### 前端

- `OrderForm`：日期输入、订单明细箱数计算、新品弹窗和订单内新品回填。
- `ProductPicker`：搜索无结果时展示“添加新品”按钮，并把当前搜索词传给表单。
- `CustomerProductEditor`：新增的四字段客户产品编辑器，与系统产品编辑器分离，避免系统字段继续泄漏到客户产品表单。
- `CustomerProductsPage`：使用简化编辑器和四字段列表。
- `PackagingTable`：改用内盒/外箱单文本尺寸列，保留多包装行能力。
- `api.ts`：日期直接传输、客户产品简化请求、新包装字段映射和旧字段兼容映射。
- `App.tsx`、`OrdersPage.tsx`：连接客户产品保存回调，使新品保存成功后能刷新列表并加入当前订单。

### 后端

- `migrate.ts`：完成新包装列和版本迁移。
- `repositories.ts`：兼容读写新旧包装数据、客户产品四字段保存和订单产品装箱数读取。
- `routes/products.ts`：解析新包装字段，同时接受旧字段。
- `routes/customer-products.ts`：接受简化的 `packCount` 请求，也继续接受历史 `packaging` 数组请求。
- `routes/orders.ts`：将新订单日期规范化为日期字符串，并保留历史日期读取能力。

接口错误继续沿用项目现有错误响应格式：校验错误返回 400，资源不存在返回 404，SKU/产品等唯一性冲突（若现有接口已校验）继续返回原错误码；本次不新增与用户界面无关的错误类型。

## 7. 测试与验收标准

### 7.1 后端和数据库测试

覆盖以下行为：

1. 迁移新数据库时创建 `inner_size`、`inner_weight`、`outer_size`；对已有数据库执行迁移后旧列和旧数据仍存在；重复迁移幂等；
2. 旧包装记录能映射出组合后的外箱尺寸，新包装记录能读回内盒/外箱单字段尺寸；可识别的三段尺寸能双写旧列；任意文本尺寸不会被截断；
3. 客户产品只传品名、SKU、规格、装箱数可以创建、读取和编辑；旧客户产品的未暴露字段不被清空；
4. 新建订单使用 `YYYY-MM-DD` 保存；旧 ISO 日期编辑后显示和保存日期部分；非法日期被拒绝；
5. 订单数量 100、装箱数 24 得到 5 箱；数量和装箱数变化会重新计算；多行订单总箱数为各行箱数之和；
6. 订单内新增品成功写入客户产品库并返回可加入订单的产品记录；校验失败不会创建产品；
7. 搜索无匹配的接口/组件状态包含可点击的“添加新品”操作。

### 7.2 前端和回归测试

- `npm run typecheck` 必须通过；
- 现有产品库、客户产品库、订单、箱唛编辑/打印、备货、发货、报价单和开单功能的既有测试继续通过；
- `npm run build` 必须通过；
- `git diff --check` 必须通过；
- 浏览器冒烟验证：新建订单日期只显示日期；搜索无产品时可打开新品弹窗；保存新品后自动出现在当前订单；选中产品后修改数量能看到 `ceil(数量/装箱数)` 的箱数；系统产品包装表能添加多行并填写内盒/外箱单字段尺寸。

## 8. 完成边界

本次实现完成后，用户可以用四个字段维护客户产品，并在新建订单时直接调用或新增客户产品；订单不再要求录入具体时间，订单箱数自动准确计算；系统产品包装信息可以按包装方式一行维护内盒和外箱数据；旧数据库字段、旧产品、旧订单、旧箱唛和既有业务流程保持可用。

不在本次实现中增加供应商备货表自动生成、客户产品与系统产品的供应商映射、包装方案优化算法或新的发货业务流程；这些功能继续沿用现有边界，等待单独需求确认。
